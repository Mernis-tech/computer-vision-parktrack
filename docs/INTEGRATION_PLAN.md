# План интеграции ParkTrack с нашей моделью

## 1. Цель

Сохранить нашу модель распознавания автомобилей и использовать ParkTrack как платформенный слой. ParkTrack будет отвечать за камеры, зоны, пользователей, хранение снимков, историю и аналитику. Наша модель будет отвечать за детекцию автомобилей.

## 2. Что уже есть

### Наша модель

- веса `best.pt` размером около 6,8 МБ;
- обработка изображений с размером входа 640 пикселей;
- подключение нескольких HLS-камер;
- прямоугольная область обработки;
- сохранение исходного и размеченного кадра;
- отправка общего количества автомобилей во внешний API.

Ограничения текущего кода: пути и часть настроек записаны внутри Python-файлов, камеры загружаются только при старте, зоны представлены прямоугольником, история хранится отдельными файлами.

### ParkTrack

- FastAPI и PostgreSQL;
- добавление и редактирование камер через админ-панель;
- многоугольные зоны на изображении;
- текущее число занятых и свободных мест;
- история наблюдений;
- исходные и размеченные снимки в MinIO;
- пользователи и права доступа;
- Docker Compose для единого запуска.

Текущий детектор ParkTrack получает одну камеру через API, берёт три кадра, выполняет OpenVINO-инференс на CPU и обновляет занятость каждой зоны.

## 3. Рекомендуемая архитектура

```text
Админ-панель
      |
      v
ParkTrack API ---- PostgreSQL
      |                |
      |                +-- камеры, зоны, история, пользователи
      v
Сервис нашей модели ---- MinIO
      |
      +-- RTSP / HLS / MP4 / HTTP-камеры
```

Модель не должна самостоятельно хранить список камер или обращаться напрямую к базе. Она получает настройки через API ParkTrack и возвращает результат через тот же API. Это позволяет позже заменить модель без переделки интерфейса и базы.

## 4. Два варианта подключения модели

### Вариант A. Адаптер Ultralytics для быстрого MVP

Создать отдельный Docker-сервис на основе нашего `best.pt` и библиотеки Ultralytics. Сервис использует API-контракты ParkTrack, но выполняет инференс существующим кодом нашей модели.

Преимущества:

- минимальный риск изменения качества;
- можно быстро сравнить результат до и после интеграции;
- не нужно сразу конвертировать модель.

Недостатки:

- Docker-образ и потребление памяти будут больше;
- PyTorch на CPU обычно тяжелее OpenVINO.

### Вариант B. Экспорт нашей модели в OpenVINO

После MVP экспортировать `best.pt` в OpenVINO и проверить совместимость выхода с пайплайном ParkTrack. Если формат сегментационной модели отличается от формата детектора ParkTrack, нужно адаптировать разбор выходных тензоров.

Преимущества:

- меньше зависимостей;
- быстрее и экономнее на CPU;
- можно использовать существующий контейнер ParkTrack.

Рекомендуемый порядок: сначала вариант A, после функциональной проверки вариант B.

## 5. Этапы работ

### Этап 0. Подготовка репозитория

- хранить два исходных проекта в одном монорепозитории;
- удалить локальные секреты, `node_modules`, сборки и временные данные;
- добавить общий `.gitignore`;
- зафиксировать исходные версии проектов и результаты контрольного теста;
- проверить лицензии компонентов перед публикацией.

Результат: оба проекта можно скачать одной командой, а секреты не попадают в историю Git.

### Этап 1. Зафиксировать контракт между платформой и моделью

Использовать следующие сущности ParkTrack:

- `GET /cameras/next` для получения активной камеры;
- `GET /zones?camera_id=...` для получения зон;
- `PUT /zones/{zone_id}` для обновления текущей занятости;
- `POST /occupancy/new` для добавления записи в историю;
- MinIO для исходного кадра, размеченного кадра и метаданных детекций.

Нужно отдельно описать JSON-запросы и ответы в Wiki. Модель не должна зависеть от внутренних таблиц PostgreSQL.

### Этап 2. Создать сервис нашей модели

- вынести пути, пороги, устройство и размер изображения в переменные окружения;
- загружать модель один раз при запуске контейнера;
- получать камеры из API вместо списка внутри Python-кода;
- поддержать RTSP, HLS, MP4 и URL изображения;
- добавить повторное подключение к недоступному потоку;
- возвращать рамки, классы и уверенность каждой детекции.

Результат: наша модель запускается как отдельный контейнер в общем `docker-compose.yml`.

### Этап 3. Подключить зоны и историю

- использовать многоугольники ParkTrack вместо прямоугольного ROI;
- считать автомобиль внутри зоны по центру рамки на первом этапе;
- для сегментационной модели позже сравнивать площадь маски с площадью зоны;
- ограничивать число занятых мест вместимостью зоны;
- сохранять исходный и размеченный кадры;
- записывать наблюдение с временем, количеством и уверенностью.

Результат: админ-панель показывает занятые и свободные места, а история содержит проверяемые снимки.

### Этап 4. Стабилизировать результат на нескольких кадрах

- получать три соседних кадра;
- оставлять детекции, подтверждённые минимум на двух кадрах;
- не обновлять зону при повреждённом кадре или недоступной камере;
- записывать причину ошибки в журнал;
- добавить тайм-ауты и ограниченное число повторных подключений.

Результат: единичная ошибка модели меньше влияет на итоговую занятость.

### Этап 5. Проверка качества

Проверить старую и интегрированную версии на одном наборе данных. Минимальный контрольный набор уже содержит 10 кадров, 604 размеченных места и 102 занятых места.

Контрольные показатели:

- F1 определения занятости;
- recall занятых мест;
- средняя ошибка количества автомобилей на кадр;
- время обработки одного цикла;
- пиковое потребление оперативной памяти;
- доля циклов с ошибкой получения потока.

После интеграции качество не должно быть хуже текущего результата нашей модели: F1 95,6 процента и средняя ошибка 0,7 автомобиля на кадр на этом контрольном наборе.

### Этап 6. Подготовка к серверу

- добавить health-check детектора;
- настроить ротацию журналов;
- ограничить срок хранения снимков;
- вынести секреты в `.env` на сервере;
- закрыть PostgreSQL и MinIO от внешнего доступа;
- настроить резервное копирование базы;
- провести нагрузочный тест на планируемом числе камер.

## 6. Критерии готовности MVP

MVP можно считать готовым, если:

1. проект поднимается одной командой Docker Compose;
2. камера добавляется через админ-панель без изменения Python-кода;
3. зона задаётся многоугольником на последнем кадре;
4. наша модель обрабатывает камеру и обновляет число занятых мест;
5. в истории сохраняются время, результат и снимки;
6. перезапуск контейнеров не удаляет базу и историю;
7. контрольный тест не показывает ухудшения качества относительно исходной модели.

## 7. Основные риски

| Риск | Что делать |
|---|---|
| Выход сегментационной модели несовместим с OpenVINO-пайплайном ParkTrack | Начать с Ultralytics-адаптера, затем отдельно выполнить экспорт |
| Разные координаты зоны и кадра | Хранить размеры кадра и масштабировать точки после обрезки |
| Один медленный поток блокирует остальные | Добавить очередь задач или отдельные процессы для камер |
| Снимки быстро заполняют диск | Ввести срок хранения и лимит объёма MinIO |
| Секреты попадут в Git | Хранить только `.env.example`, включить проверку секретов в CI |
| Лицензии не позволяют свободно объединять код | Сохранить исходные LICENSE и проверить каждый компонент до публикации |
