# Организация Git-репозитория

## 1. Формат репозитория

Для учебного проекта рекомендуется монорепозиторий. Он позволяет одной командой получить модель, ParkTrack, общую документацию и будущий интеграционный сервис.

Не следует добавлять ParkTrack и нашу модель как вложенные `.git`-репозитории. В этой сборке история исходных проектов не копируется, а ссылки на оригиналы указаны в корневом README.

## 2. Ветки

- `main` — проверенная версия, которую можно показать преподавателю;
- `develop` — общая ветка разработки;
- `feature/...` — отдельная задача;
- `fix/...` — исправление ошибки;
- `docs/...` — документация и Wiki.

Примеры:

```text
feature/model-adapter
feature/polygon-zones
fix/camera-reconnect
docs/server-installation
```

## 3. Правило работы

1. Создать задачу в Issues.
2. Создать ветку от `develop`.
3. Сделать небольшие логические коммиты.
4. Открыть Pull Request в `develop`.
5. Другой участник проверяет код и инструкцию запуска.
6. После демонстрационной проверки изменения переходят в `main`.

## 4. Формат коммитов

```text
feat: add ParkTrack API adapter
fix: reconnect unavailable HLS stream
docs: add camera setup guide
test: add occupancy comparison dataset
chore: update Docker Compose
```

## 5. Что не должно попадать в Git

- `.env` и реальные секреты;
- пароли администратора;
- закрытые URL камер;
- `node_modules` и виртуальные окружения;
- дампы базы;
- снимки с камер и журналы;
- сборки `dist`;
- временные результаты модели.

## 6. Создание репозитория на GitHub

1. Создать пустой репозиторий без README и лицензии.
2. Скопировать его HTTPS- или SSH-адрес.
3. В корне этой папки выполнить:

```bash
git remote add origin <URL_РЕПОЗИТОРИЯ>
git push -u origin main
```

4. Создать ветку разработки:

```bash
git switch -c develop
git push -u origin develop
```

5. Защитить `main`: запретить прямой push и требовать Pull Request.

Если GitHub отклонит будущий файл модели размером более 100 МБ, нужно использовать Git LFS или хранить веса как отдельный релиз.
